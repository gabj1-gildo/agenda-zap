## COMO USAR ESTE DOCUMENTO

Este plano tem **5 fases sequenciais com gates de bloqueio**. Cada fase só pode começar depois que a anterior for **explicitamente aprovada por você** (o humano), não pelo agente sozinho.

Cole o bloco "PROMPT MESTRE" inteiro na primeira mensagem para o agente. Ele vai executar **apenas a Fase 0** e parar. Depois de você revisar e aprovar, mande "aprovado, siga para Fase 1" — e assim por diante.

**Não cole todas as fases de uma vez pedindo para o agente "fazer tudo".** Isso é proposital: quanto maior o escopo dado de uma vez, maior a chance do agente pular validação, misturar migração de schema com mudança de lógica de negócio, ou "otimizar" algo que não foi pedido. Uma fase por vez, com revisão sua no meio, é o que garante que nada importante seja pulado.

## FASE 0 — Segurança crítica (hotfix, sem tocar em IA/schema)

**Objetivo:** eliminar acesso não autenticado a rotas que hoje permitem ler/alterar dados de qualquer empresa.

**Escopo — apenas estas rotas:**
- `GET/PATCH /api/settings/tenant`
- `GET/PUT /api/settings/schedules`
- `GET/POST /api/settings/payment-keys`
- `PATCH/DELETE /api/settings/payment-keys/[id]`
- `PATCH /api/clients/[id]`
- `GET /api/tenants/[id]/agenda`
- `GET/POST /api/tenants/[id]/settings`

**Instruções específicas para o agente:**
1. Verifique como `verifyAuth` e `withTenant()` são usados hoje nas rotas que JÁ funcionam corretamente (ex: `/api/chats`, `/api/dashboard/*`) e replique o mesmo padrão — não crie um padrão de auth novo.
2. Para cada rota do escopo, adicione: (a) exigência de usuário autenticado, (b) verificação de que o usuário autenticado tem vínculo com o `tenantId`/`tenant-id` sendo acessado (via `user_tenants`).
3. Para `PATCH /api/clients/[id]`: adicionar tanto autenticação quanto filtro `WHERE id = X AND tenant_id = Y` na query — hoje falta os dois.
4. Não altere a lógica de negócio dessas rotas, apenas a camada de autenticação/autorização.
5. Webhook do WhatsApp (`/api/webhooks/whatsapp`) fica **fora do escopo** — ele é intencionalmente público e usa isolamento via `instanceName`, não mexer.

**Critérios de Aceite (o agente deve verificar um por um):**
- [ ] Uma requisição sem token válido para cada uma das 7 rotas retorna 401/403 (não 200)
- [ ] Uma requisição autenticada como usuário do Tenant A tentando acessar/alterar dado do Tenant B retorna 403 (não sucesso)
- [ ] `PATCH /api/clients/[id]` valida tenant_id do client contra o tenant do usuário autenticado
- [ ] Nenhuma rota fora do escopo definido foi alterada
- [ ] Rotas que já tinham auth funcionando continuam funcionando (não quebrou nada existente)

**⚠️ Gate de bloqueio:** não seguir para Fase 1 sem eu confirmar que testei manualmente pelo menos 2 dessas rotas.

## FASE 1 — Tabela `services` estruturada

**Objetivo:** parar de depender de texto livre (`aiConfig.servicos_precos`) para preço e nome de serviço, que hoje é decidido pela IA por interpretação de texto — risco direto de cobrança errada.

**Escopo:**
1. Criar tabela `services` (tenantId, name, price, durationMinutes, isActive, timestamps).
2. Adicionar campo `serviceId` (nullable, FK) em `appointments` — **sem remover `serviceName`**.
3. Criar um script de migração de dados (não uma migration de schema — um script à parte, rodado manualmente por mim) que:
   - Lê `tenants.aiConfig.servicos_precos` de cada tenant
   - Tenta fazer parse do texto (formato usual: `Nome = R$Valor` separado por `|` ou quebra de linha)
   - Insere os serviços encontrados em `services`, com `durationMinutes` default de 30 se não especificado
   - Gera um relatório (arquivo texto/CSV) listando: tenant, quantos serviços foram extraídos com sucesso, quantos falharam o parse e precisam de revisão manual
4. Criar endpoint novo para CRUD de `services` (`GET/POST/PATCH/DELETE /api/settings/services`), seguindo o mesmo padrão de auth da Fase 0.
5. **Não alterar ainda** a tela de "Serviços e Preços" no frontend nem a tool `create_appointment` — isso é Fase 3.

**Critérios de Aceite:**
- [ ] Migration de schema gerada e revisada (não aplicada sem minha aprovação)
- [ ] Script de migração de dados rodado em ambiente de teste/staging (não produção) e relatório de sucesso/falha gerado
- [ ] Endpoint de CRUD de `services` funcionando com autenticação e filtro de tenant
- [ ] `serviceName` em `appointments` continua existindo e funcionando (nada quebrado)
- [ ] Relatório mostra claramente quantos tenants tiveram parse 100% automático vs. quantos precisam de revisão manual antes de irmos para produção

**⚠️ Gate de bloqueio:** não seguir para Fase 2 sem eu revisar o relatório de migração de dados e decidir o que fazer com os tenants que falharam o parse automático.

## FASE 2 — Horários estruturados, antecedência e exceções

**Objetivo:** eliminar a segunda fonte de verdade conflitante (texto livre `horario_funcionamento` vs. tabela `schedules` que já existe mas não é usada pela IA), e adicionar regras de antecedência mínima/máxima.

**Escopo:**
1. Adicionar campos `minAdvanceMinutes` (default 60) e `maxAdvanceDays` (default 30) — decidir com base no schema atual se ficam em `tenants` ou em tabela nova `booking_rules` (o agente deve justificar a escolha no relatório, não decidir silenciosamente).
2. Criar tabela `schedule_exceptions` (tenantId, date, isClosed, customStartTime, customEndTime).
3. Criar endpoint de CRUD para exceções de horário, mesmo padrão de auth.
4. **Não conectar ainda** com a IA/prompt — isso acontece na Fase 3.
5. Frontend: pode already trocar a textarea de "Horário de Funcionamento" por formulário estruturado que grava em `schedules` (essa tabela já existe e já está correta), mas manter o campo antigo salvo em paralelo até a Fase 4.

**Critérios de Aceite:**
- [ ] Tabela `schedule_exceptions` criada e testada com pelo menos um caso de feriado bloqueado
- [ ] Campos de antecedência mínima/máxima existem e têm valores default sensatos
- [ ] Endpoint de CRUD funcionando com auth
- [ ] Decisão de onde ficam os campos de antecedência está documentada no relatório com justificativa

**⚠️ Gate de bloqueio:** não seguir para Fase 3 sem confirmar que `schedules` + `schedule_exceptions` juntas conseguem responder corretamente "esse horário está aberto?" para pelo menos 3 cenários de teste que eu vou fornecer (dia normal, dia de exceção fechado, exceção com horário customizado).

## FASE 3 — Tools de IA: `check_availability`, `list_services`, revisão de `create_appointment`

**Objetivo:** a IA para de "decidir" preço e horário por texto e passa a **consultar o banco** via function calling. Esta é a fase que resolve o risco mais caro (cobrança errada, agendamento duplicado).

**Escopo:**
1. Criar tool `check_availability(serviceId, date)`:
   - Busca `durationMinutes` do serviço
   - Cruza com `schedules` do dia da semana
   - Subtrai `appointments` já existentes (status PENDENTE ou PAGO) naquele dia
   - Aplica `schedule_exceptions` se houver
   - Aplica `minAdvanceMinutes`/`maxAdvanceDays`
   - Retorna lista de slots livres
2. Criar tool `list_services()`:
   - Retorna `services` ativos do tenant (nome, preço, duração)
3. Revisar `create_appointment`:
   - Trocar parâmetros de `serviceName + price` (texto livre decidido pela IA) para `serviceId` apenas
   - O handler busca o preço real em `services` pelo `serviceId` — a IA nunca envia preço
   - Antes de inserir, o handler deve re-checar disponibilidade (mesma lógica de `check_availability`) para evitar condição de corrida entre dois clientes pedindo o mesmo slot ao mesmo tempo
4. Atualizar o system prompt para instruir a IA a **sempre** chamar `list_services` e `check_availability` antes de propor serviço/horário, nunca decidir por texto do `aiConfig`.
5. **Manter** `servicos_precos` e `horario_funcionamento` no `aiConfig` por enquanto (deprecated, não removidos) — a remoção definitiva é decisão sua, fora deste plano.

**Critérios de Aceite:**
- [ ] `check_availability` testada com um tenant real de staging, retornando slots corretos considerando conflitos existentes
- [ ] `list_services` retorna exatamente os dados da tabela `services`, sem depender de texto do `aiConfig`
- [ ] `create_appointment` não aceita mais preço vindo da IA — preço sempre lido do banco
- [ ] Teste manual de condição de corrida: duas requisições simultâneas para o mesmo slot — apenas uma deve ter sucesso
- [ ] Prompt atualizado instruindo a IA a usar as tools antes de responder sobre disponibilidade/preço

**⚠️ Gate de bloqueio:** não seguir para Fase 4 sem eu validar em uma conversa de teste real via WhatsApp (staging) que a IA está de fato chamando as tools e não inventando horário/preço.

## FASE 4 — Hardening do prompt e redução de superfície de texto livre

**Objetivo:** com serviços e horários já estruturados (saíram do prompt), reduzir o que resta de texto livre e mitigar risco de prompt injection vindo da configuração do lojista.

**Escopo:**
1. Reestruturar o prompt para delimitar claramente blocos de configuração do lojista (tom, restrições, transbordo, pagamento, encerramento) com marcadores explícitos, deixando claro no prompt principal que instruções dentro desses blocos não sobrepõem regras de segurança/fluxo.
2. Adicionar limite de tamanho de caracteres nos campos de texto livre restantes (defina um número e justifique).
3. Adicionar validação básica no endpoint de salvamento do `aiConfig` (hoje aceita qualquer JSON sem checagem) — validar que as chaves esperadas existem e respeitam o limite de tamanho.
4. Remover do prompt as seções `servicos_precos` e `horario_funcionamento` (já não são mais necessárias, pois a IA consulta via tools) — mas manter os campos no banco/JSON como deprecated, não apagar dado do cliente.

**Critérios de Aceite:**
- [ ] Prompt final não injeta mais texto livre de serviços/horários
- [ ] Teste de prompt injection: escrever algo adversarial em "Restrições" (ex: instrução para ignorar regras de segurança) e confirmar que o comportamento da IA não muda
- [ ] Validação de tamanho/formato ativa no endpoint de salvamento
- [ ] Relatório final resumindo o que ainda ficou como texto livre por decisão consciente (tom, restrições, transbordo) e por quê

**⚠️ Este é o fim do plano.** Ao final da Fase 4, peça ao agente um relatório consolidado geral (todas as 5 fases) para você arquivar como documentação do que foi feito.
